# Systematic Debug 系统化调试流程

本 Skill 的目标不是：

让当前示例能够通过。

真正目标是：

**找到错误根因，并确保修改不会破坏其他情况。**

# 阶段一：复现问题

修改任何代码之前：

1. 运行出现问题的测试、命令或 Demo。
2. 记录真实输出。
3. 明确预期输出。
4. 确认问题确实存在。
5. 找到最小可复现案例。

记录：

实际结果：

预期结果：

出现日期：

相关股票：

相关板块：

相关模块：

如果无法复现：

先调查为什么无法复现。

禁止在无法复现问题的情况下直接猜测并修改代码。

# 阶段二：追踪完整数据流

从最终错误结果向上游追踪。

例如：

Demo 输出错误

↓

龙头最终结果

↓

多股票 PK

↓

股票评分

↓

板块状态

↓

板块评分

↓

股票基础特征

↓

原始行情数据

对于每一个关键节点记录：

INPUT

CALCULATION

OUTPUT

不要只检查最终显示错误结果的函数。

# 阶段三：建立 Root Cause 假设

根据数据流提出可能原因。

例如：

* 日期错位
* 状态没有 reset
* 状态过早 reset
* rolling window 有 off-by-one
* 权重错误
* normalization 错误
* filter 顺序错误
* 排名方向错误
* 阈值错误
* 缺失数据处理错误
* 生命周期转换错误
* 第二波逻辑缺失
* 使用未来数据
* demo 输入和生产输入不同

每一个假设必须寻找证据。

证据来源包括：

* 源代码
* Runtime value
* Log
* 测试
* 历史数据
* 中间计算结果

没有证据支持的假设必须被淘汰。

# 阶段四：确定真正 Root Cause

修改代码之前必须回答：

为什么最终结果会错误？

具体是哪一个条件、变量、状态、时间窗口或数据导致？

错误第一次出现在哪个阶段？

为什么旧代码会出现这种行为？

禁止只写：

“生命周期逻辑有问题。”

必须尽可能具体，例如：

“退潮状态退出条件只允许进入 rebound，
而 rebound 状态缺少基于连续强度恢复和前高突破的
second_wave transition，因此板块在重新启动后仍长期停留于 rebound。”

# 阶段五：建立 Regression Test

如果问题可以稳定复现：

先建立回归测试。

要求：

修复前 FAIL。

修复后 PASS。

优先测试：

业务行为。

不要测试：

内部函数具体写法。

禁止为了让测试通过而直接修改 expected value。

# 阶段六：实施最小修改

只修复导致问题的根因。

禁止：

* 顺便重构大量无关代码
* 调整无关参数
* 修改无关评分
* 修改无关状态
* 针对日期 hardcode
* 针对股票代码 hardcode
* 针对板块 hardcode
* 增加 demo-only logic
* 删除暴露错误的数据
* 使用 fallback 隐藏错误

如果需要较大架构调整：

先证明为什么最小修改不能正确解决问题。

# 阶段七：Build

执行项目真实 Build。

如果 Build 失败：

继续修复。

不得绕过 Build。

# 阶段八：自动测试

运行：

现有测试

*

相关模块测试

*

新增 Regression Test

任何相关测试失败：

继续调查。

禁止通过删除测试解决。

# 阶段九：运行真实 Demo

必须尽量运行真实业务路径。

禁止只调用人为构造的小函数证明修改有效。

需要确认：

真实输入

↓

真实算法

↓

真实输出

完整链路可以正常工作。

# 阶段十：时间序列检查

对于以下问题：

* 生命周期
* 市场排名
* 龙头
* 趋势
* 第二波
* 多日评分

必须检查目标日期附近数据。

最低：

T-2

T-1

T

T+1

T+2

如果属于较长生命周期转换：

检查更长窗口。

例如：

T-10 ～ T+5。

# 阶段十一：多样本验证

禁止只检查发生问题的对象。

如果问题发生在：

半导体

还需要检查其他类似板块。

如果问题发生在：

某一只龙头股

还需要检查其他股票。

如果问题发生在：

一个历史日期

还需要检查其他日期。

目的：

防止出现针对单一案例的过拟合修复。

# 阶段十二：对抗性测试

主动寻找当前修改可能失败的情况。

至少考虑：

* 空数据
* NaN
* 缺失数据
* 重复数据
* 阈值恰好相等
* Top N 边界
* 平分
* 连续涨
* 连续跌
* 一日暴涨
* 一日暴跌
* 急跌后弱反弹
* 急跌后强反弹
* 连续修复
* 二次启动
* 第二波
* 龙头掉队
* 龙头切换

# 阶段十三：检查未来数据泄漏

任何涉及时间序列的修改必须检查：

计算 T 日结果时，

是否使用了：

T+1

或任何未来信息。

重点检查：

* shift
* rolling
* expanding
* merge
* join
* forward fill
* label
* future return
* high / low window
* 排名数据

Future Data Leakage 属于严重错误。

# 阶段十四：Git Diff Review

查看所有修改。

逐行检查：

* 是否存在无关修改
* 是否引入 hardcode
* 是否存在临时调试逻辑
* 是否增加魔法数字
* 是否修改默认行为
* 是否吞异常
* 是否降低 validation
* 是否存在重复计算
* 是否改变历史含义
* 是否存在日期特殊判断
* 是否存在股票代码特殊判断
* 是否存在板块特殊判断

# 完成门槛

必须满足：

Root Cause 已确认

*

Regression Case 已建立（适用时）

*

Build 成功

*

相关 Tests 通过

*

真实 Demo 已运行

*

实际输出已人工检查

*

时间序列附近日期已检查

*

没有发现明显回归

*

Git Diff 已 Review

才能报告任务完成。

如果其中任何重要步骤失败：

继续 Debug。

# 最终输出

完成时报告：

## Root Cause

错误的真正原因。

## Fix

实施了什么最小修复。

## Files

修改了哪些文件。

## Tests

运行了哪些测试。

## Demo

运行了什么真实 Demo。

## Result

观察到的真实结果。

## Regression Risk

可能影响什么。

## Remaining Risk

还有什么没有验证。

禁止在没有完成验证时声称：

“完全解决”。
